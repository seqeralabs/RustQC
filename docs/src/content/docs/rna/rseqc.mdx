<Aside type="note" title="About RSeQC">
RSeQC is a Python package providing a suite of quality control tools for RNA-Seq data, including strandedness inference, read distribution analysis, junction annotation, and more.

[Documentation](https://rseqc.sourceforge.net/) | [Source code](https://github.com/MonashBioinformaticsPlatform/RSeQC)
</Aside>

RustQC reimplements nine tools from the [RSeQC](https://rseqc.sourceforge.net/)
package (including TIN and split_bam). Each tool produces output files that match the format
and content of the original Python implementation, plus **native PNG and SVG
plots** generated directly -- no R scripts required.

All RSeQC tools except split_bam (which needs a BED file) run automatically
as part of the `rustqc rna` command and use
the input filename stem as a prefix for output files. Output files are organized
into per-tool subdirectories under `rseqc/`. For example,
`rustqc rna sample.bam --gtf genes.gtf -o results/` produces
RSeQC output files like `results/rseqc/bam_stat/sample.bam_stat.txt`.

Use `--flat-output` to write all files directly to the output directory instead
of the nested `rseqc/<tool>/` subdirectories.

<Aside type="tip" title="About benchmarks">
Each tool section below includes benchmark comparisons against the original RSeQC tools,
validated on two datasets from an AWS cloud run (nf-core AWS megatests, 2026-03-09):

- **Small dataset**: `test.bam` - ~52K reads, chr6 subset
- **Large dataset**: `GM12878_REP1.markdup.sorted.bam` - ~186M reads (GM12878 ENCODE RNA-Seq)

Both upstream RSeQC (v5.0.4) and RustQC ran on the same BAM files. RustQC uses GTF directly; RSeQC uses BED12 derived from the same Ensembl GTF.
</Aside>

| File                  | Description                                                                                                                           |

## infer_experiment

Library strandedness inference by sampling reads overlapping gene models.

| File                          | Description                                                               |
| ----------------------------- | ------------------------------------------------------------------------- |
| `{stem}.infer_experiment.txt` | Strandedness fractions: failed-to-determine, and the two strand protocols |

The output reports the fraction of reads consistent with each strand protocol:

- **Fraction failed to determine** -- reads that could not be assigned to either protocol
- **Fraction "1++,1--,2+-,2-+"** (forward stranded) -- reads consistent with the same-strand protocol
- **Fraction "1+-,1-+,2++,2--"** (reverse stranded) -- reads consistent with the opposite-strand protocol

For paired-end data, the labels are `PairEnd` with `1++,1--,2+-,2-+` and
`1+-,1-+,2++,2--`. For single-end: `SingleEnd` with `++,--` and `+-,-+`.

**Interpreting results:**

- Both fractions near 50% = unstranded library
- First fraction near 100% = forward stranded (e.g., Ligation protocol)
- Second fraction near 100% = reverse stranded (e.g., dUTP protocol, most common)

**Strandedness mismatch warning:**
RustQC automatically compares the infer_experiment results against the
`--stranded` flag you specified. If they disagree, a warning is printed
at the end of the run suggesting the correct value:

The difference is caused by a read-sampling mismatch: the upstream
`infer_experiment.py` defaults to sampling only 200,000 reads. On a 186M-read BAM,
this early-file subsample draws predominantly from the first few chromosomes, which
underrepresents loci where transcripts on both strands overlap, causing the
"failed-to-determine" fraction to appear lower than it truly is. RustQC processes
all reads, giving a more representative estimate.

Both tools correctly identify the library as strongly reverse-stranded
(antisense ~88-92%), so the practical interpretation is identical.

## read_duplication

Position-based and sequence-based duplication rate histograms.

| File                      | Description                                                                        |
| ------------------------- | ---------------------------------------------------------------------------------- |
| `{stem}.pos.DupRate.xls`  | Position-based duplication histogram (TSV: Occurrence, UniqReadNumber, ReadNumber) |
| `{stem}.seq.DupRate.xls`  | Sequence-based duplication histogram (TSV: Occurrence, UniqReadNumber, ReadNumber) |
| `{stem}.DupRate_plot.r`   | R script for generating duplication rate plots (matching RSeQC format)             |
| `{stem}.DupRate_plot.png` | Duplication rate plot (PNG)                                                        |
| `{stem}.DupRate_plot.svg` | Duplication rate plot (SVG)                                                        |

Each TSV file is a tab-separated table where each row represents a duplication
level (number of times a read was seen). The columns are:

- **Occurrence** -- the duplication count (1 = unique, 2 = seen twice, etc.)
- **UniqReadNumber** -- number of unique read groups at this duplication level
- **ReadNumber** -- total reads consumed (Occurrence x UniqReadNumber)

Position-based deduplication groups reads by alignment position (chromosome,
start, CIGAR-derived exon blocks). Sequence-based deduplication groups reads by
the actual read sequence.

The duplication rate plot shows two curves: **mapping-based** (blue, x markers)
and **sequence-based** (red, dot markers) duplication. The x-axis shows the
occurrence count (capped at 500) and the y-axis shows the number of reads at
each duplication level. Most reads should appear at low occurrence counts; a
long tail indicates high duplication.

## junction_annotation

Splice junction classification against a reference gene model.

| File                             | Description                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `{stem}.junction.xls`            | TSV with all observed junctions: chrom, intron_start(0-based), intron_end(1-based), read_count, annotation_status |
| `{stem}.junction.bed`            | BED12 file with color-coded junctions (red = known, green = partial novel, blue = complete novel)                 |
| `{stem}.junction_plot.r`         | R script for generating splice event and junction pie charts                                                      |
| `{stem}.splice_events.png`       | Splice events pie chart (PNG)                                                                                     |
| `{stem}.splice_events.svg`       | Splice events pie chart (SVG)                                                                                     |
| `{stem}.splice_junction.png`     | Splice junctions pie chart (PNG)                                                                                  |
| `{stem}.splice_junction.svg`     | Splice junctions pie chart (SVG)                                                                                  |
| `{stem}.junction_annotation.log` | Summary: total/known/partial novel/complete novel event and junction counts                                       |

Junctions are classified by comparing splice sites (CIGAR N-operations)
against the reference gene model:

- **Known (Annotated)** -- both donor and acceptor sites match known introns
- **Partial novel** -- one splice site matches, the other is novel
- **Complete novel** -- neither splice site matches any known intron

Two pie charts are generated, one for splice **events** (reads) and one for
splice **junctions** (unique splice sites). Each chart shows the proportion of
known (blue), partial novel (red), and complete novel (green) splicing.

## junction_saturation

Splice junction discovery rate at increasing sequencing depths.

| File                                    | Description                                                            |
| --------------------------------------- | ---------------------------------------------------------------------- |
| `{stem}.junctionSaturation_plot.r`      | R script for saturation curve plots                                    |
| `{stem}.junctionSaturation_plot.png`    | Junction saturation plot (PNG)                                         |
| `{stem}.junctionSaturation_plot.svg`    | Junction saturation plot (SVG)                                         |
| `{stem}.junctionSaturation_summary.txt` | TSV: percent_of_reads, known_junctions, novel_junctions, all_junctions |

The tool subsamples reads at configurable percentages (default: 5%, 10%, ...,
100%) and counts how many unique known and novel junctions are detected at each
level. This reveals whether sequencing depth is sufficient for full
junction detection. A saturated library will show a plateau in the curve; an
unsaturated library will show continuing growth.

The junction saturation plot shows three lines: **all junctions** (blue),
**known junctions** (red), and **novel junctions** (green). The x-axis is the
percentage of total reads used and the y-axis is the number of splice junctions
detected (in thousands). A plateau in the curves indicates saturation.

RustQC follows RSeQC's sampling: the percentages are
`range(floor, ceiling, step)` followed by 100, and the window for each percentage
uses RSeQC's floating-point index arithmetic, `int(N * (p / 100.0))`. The x-axis
values are therefore identical to RSeQC's, and so is the 100% point whenever the
windows cover all observations (as with the default parameters). The
intermediate points depend on how the splice-junction observations are shuffled.
RSeQC does not seed Python's `random`, so its intermediate points change from run
to run. RustQC shuffles with its own seeded RNG (`--junction-saturation-seed`,
default 42), so its intermediate points are reproducible and identical for any
`--threads` value, but they do not match RSeQC's random draws.

As in RSeQC, reads on chromosomes without any annotated transcript are ignored.
The `pdf()` call in the R script names the PDF by sample name only, as RSeQC does
when run with `-o <sample name>`, so the script does not depend on the output
directory.

## inner_distance

Fragment inner distance for paired-end RNA-seq libraries.

| File                                | Description                                                    |
| ----------------------------------- | -------------------------------------------------------------- |
| `{stem}.inner_distance.txt`         | Per-pair detail: readpair_name, inner_distance, classification |
| `{stem}.inner_distance_freq.txt`    | Histogram: lower_bound, upper_bound, count                     |
| `{stem}.inner_distance_plot.r`      | R script for histogram and density plot                        |
| `{stem}.inner_distance_plot.png`    | Inner distance histogram with density overlay (PNG)            |
| `{stem}.inner_distance_plot.svg`    | Inner distance histogram with density overlay (SVG)            |
| `{stem}.inner_distance_summary.txt` | Summary counts by pair classification                          |

The inner distance is defined as the gap between the end of read 1 and the
start of read 2 on the mRNA transcript. Negative values indicate read overlap.
Pairs are classified as:

- **sameTranscript=Yes, sameExon=Yes** -- both reads on the same exon
- **sameTranscript=Yes, sameExon=No** -- reads on the same transcript, different exons (distance calculated on mRNA)
- **sameTranscript=No** -- reads on different transcripts or no transcript overlap
- **readPairOverlap** -- reads overlap each other
- **nonExonic** -- one or both reads not on exons
- **sameChrom=No** -- reads on different chromosomes
- **unknownChromosome** -- chromosome not in the gene model

The histogram bins are configurable via `--inner-distance-lower-bound`,
`--inner-distance-upper-bound`, and `--inner-distance-step` (defaults: -250 to 250, step 5).

The inner distance plot is a histogram showing the distribution of fragment
inner distances, with a Gaussian density curve (red) overlaid. The title
displays the mean and standard deviation. The distribution should be
approximately normal for a well-prepared library.

## TIN (Transcript Integrity Number)

TIN (Transcript Integrity Number) measures the uniformity of read coverage
across a transcript. A TIN score of 100 means perfectly uniform coverage; lower
scores indicate degradation or bias. TIN is computed using Shannon entropy of
per-base read coverage at sampled positions along each transcript's exonic regions.

RustQC reimplements [RSeQC's `tin.py`](https://rseqc.sourceforge.net/#tin-py),
computing TIN scores automatically as part of `rustqc rna` in the same
single-pass BAM scan as all other analyses.

TIN is particularly useful for:

- Detecting RNA degradation: degraded samples show low TIN scores across
  most transcripts
- Sample QC: median TIN provides a single-number summary of RNA integrity,
  complementing RIN (RNA Integrity Number) from Bioanalyzer/TapeStation
- Identifying problematic samples: samples with unusually low median TIN
  should be flagged for potential exclusion

| File                 | Description                                                            |
| -------------------- | ---------------------------------------------------------------------- |
| `{stem}.tin.xls`     | Per-transcript TIN scores (TSV: geneID, chrom, tx_start, tx_end, TIN)  |
| `{stem}.summary.txt` | Summary statistics: mean, median, and standard deviation of TIN scores |

### TIN scores file

The `{stem}.tin.xls` file is a tab-separated file with one row per transcript:

| Column     | Description                         |
| ---------- | ----------------------------------- |
| `geneID`   | Transcript identifier (as `tin.py`) |
| `chrom`    | Chromosome                          |
| `tx_start` | Transcript start position           |
| `tx_end`   | Transcript end position             |
| `TIN`      | Transcript Integrity Number (0-100) |

Transcripts below the minimum coverage threshold are reported with a TIN of `0.0`
and are left out of the summary statistics, as in `tin.py`. TIN values are written
at full precision, like Python's `str(float)`.

Rows follow the BED order produced by nf-core/rnaseq's `eautils/gtf2bed` module.
The converter sorts by chromosome name, the start of each transcript's first
exon line in the GTF, then transcript ID. Exons without a transcript ID are omitted.
Older versions of the converter break ties in Perl hash order, which varies between runs.

### Summary file

The `{stem}.summary.txt` file is a single-row tab-separated summary:

| Column        | Description                                 |
| ------------- | ------------------------------------------- |
| `Bam_file`    | File name of the input BAM                  |
| `TIN(mean)`   | Mean TIN across all transcripts             |
| `TIN(median)` | Median TIN                                  |
| `TIN(stdev)`  | Standard deviation (population) of TIN      |

The statistics are computed as NumPy computes them in `tin.py` (pairwise
summation), over the transcripts that passed the coverage threshold. If none
pass, the summary reports `nan` for all three statistics.

### Interpreting TIN scores

| Median TIN | Interpretation                                |
| ---------- | --------------------------------------------- |
| > 70       | Good RNA integrity                            |
| 50-70      | Moderate degradation                          |
| < 50       | Significant degradation -- consider excluding |
| < 30       | Severe degradation                            |

A bimodal distribution of per-transcript TIN scores (some very high, some very
low) can indicate selective degradation of certain transcript classes rather
than global degradation.

### Configuration

TIN parameters (`sample_size`, `min_coverage`) can be set in the YAML config file.
See the [Configuration](../usage/configuration/#tin) page for details.
Like `tin.py`, TIN does not filter reads by mapping quality.

### Performance

The upstream `tin.py` tool processes each transcript independently and scales
poorly with BAM size. On large production datasets (e.g., ~186M reads), `tin.py`
can take **over 9 hours** and may fail to complete within typical pipeline time limits.
RustQC computes TIN scores as part of its single-pass BAM scan, completing all
analyses combined in under 15 minutes.

### Compatibility

RustQC's TIN output uses the same file format and column names as RSeQC's
`tin.py`. TIN scores are computed using the same Shannon entropy formula.

`tin.py` counts coverage with pysam's `pileup()` and its default settings, and
RustQC reproduces what that pileup counts at each sampled position:

- Reads flagged unmapped, secondary, QC-fail or duplicate are not counted, and
  neither are orphans (paired reads without the proper-pair flag).
- Bases with a base quality below 13 are not counted.
- Overlapping mates are counted once. RustQC replays htslib's overlap quality
  adjustment (`tweak_overlap_quality`, htslib 1.24 as bundled with pysam 0.24),
  including its quirks after deletions and reference skips.
- Deleted and skipped (`N`) bases are not counted. A transcript that passes the
  minimum read check but has no counted base gets `100 / l` when some read spans
  a sampled position, and `0` otherwise, as in `tin.py`.

The one pileup setting not reproduced is the `max_depth` cap of 8,000 reads per
position, which only matters for extremely deep transcripts.

## split_bam

RustQC reimplements [RSeQC's `split_bam.py`](https://rseqc.sourceforge.net/#split-bam-py),
which classifies every alignment against a BED file of regions. Its main use is
**rRNA quantification** with an rRNA BED file (for example RSeQC's
[`hg38_rRNA.bed`](https://sourceforge.net/projects/rseqc/files/BED/Human_Homo_sapiens/)).
This counts rRNA that the GTF/biotype route cannot see; see
[why biotype rRNA can read near zero](../featurecounts/#rrna-and-biotype-counts).

Unlike the other RSeQC tools, split_bam needs an extra input, so it only runs
when a BED file is given:

```bash
rustqc rna sample.markdup.bam --gtf genes.gtf --split-bam-bed hg38_rRNA.bed
```

Each alignment record falls into exactly one category:

| Category | Records                                                                    |
| -------- | -------------------------------------------------------------------------- |
| `in`     | Mapped, QC-passing records whose start (or mate's start) is in a region    |
| `ex`     | Mapped, QC-passing records outside every region                            |
| `junk`   | QC-failed (`0x200`) or unmapped (`0x4`) records                            |

Classification follows `split_bam.py` exactly:

- The BED file is read as **BED12**, and only the exon blocks count. A read
  starting inside an intron of a BED12 record is `ex`.
- A record is `in` when its own 0-based start lies in a block on its
  chromosome. If the mate-unmapped flag (`0x8`) is not set, the mate's start is
  also tested, **against the read's own chromosome** even when the mate maps
  elsewhere.
- Only the start position is tested, not the whole alignment.
- No other flags are filtered. Secondary, supplementary and duplicate
  alignments are all classified, so multi-mapping rRNA reads count once per
  reported alignment.
- Chromosome names are compared case-insensitively against the **alignment
  file's** reference names. The `chromosome_prefix` / `chromosome_mapping`
  settings (which map alignment names to GTF names) do not apply.

RustQC warns when no BED chromosome matches any reference name in the
alignment file (for example a `chr6` BED against an Ensembl `6` BAM), a mismatch
that `split_bam.py` silently reports as 0% `in`.

| File                       | Description                                   |
| -------------------------- | --------------------------------------------- |
| `{stem}.split_bam.txt`     | Record counts, identical to `split_bam.py`'s stdout |
| `{stem}.in.bam`            | Records in the regions (optional)             |
| `{stem}.ex.bam`            | Records outside the regions (optional)        |
| `{stem}.junk.bam`          | QC-failed and unmapped records (optional)     |

The summary file is byte-for-byte what `split_bam.py -o {stem}` prints. For
the test fixture (`tests/expected/split_bam/split_bam_test.split_bam.txt`):

```text
Total records:                                         33
split_bam_test.in.bam (Alignments consumed by input gene list):15
split_bam_test.ex.bam (Alignments not consumed by input gene list):11
split_bam_test.junk.bam (qcfailed, unmapped reads):    7
```

### Writing the split BAM files

The counts come from the single pass. Writing the `.in.bam`, `.ex.bam` and
`.junk.bam` files is optional because it needs one extra sequential read of the
alignment file:

```bash
rustqc rna sample.markdup.bam --gtf genes.gtf \
  --split-bam-bed hg38_rRNA.bed --split-bam-write-bams
```

The BAM files keep the input header unchanged and the records in input order,
matching `split_bam.py`.

### Configuration

split_bam can also be enabled from the config file. See the
[Configuration](../usage/configuration/#split_bam) page.

### Compatibility

Validated against RSeQC 5.0.4 `split_bam.py`:

- **Test fixture** (`tests/data/split_bam_test.*`): 33 records covering every
  classification branch, with a BED12 that has multi-block, zero-length,
  overlapping, truncated-block and mixed-case entries. Counts and all three
  BAM files are identical, record for record.
- **Small dataset** (~52K reads, chr6 subset): with a 4,000-record BED12
  built around the reads, the counts (32,150 `in` / 20,689 `ex`) and all three
  BAM files are identical to `split_bam.py` on both the single-threaded and
  the parallel code paths.

BED inputs that `split_bam.py` crashes on are accepted. Blank, `#`, `track` and
`browser` lines are skipped, and BED3–BED11 records are used as a single
`chromStart`–`chromEnd` block, with a warning.

## Compatibility with RSeQC

All output files are designed to be drop-in replacements for the corresponding
RSeQC Python tool output. File formats, column names, and numeric precision
match the Python originals to facilitate migration from RSeQC to RustQC without
downstream pipeline changes.

RustQC also generates the R scripts that RSeQC produces (for junction_annotation,
junction_saturation, inner_distance, and read_duplication), maintaining full
compatibility. However, unlike RSeQC, **RustQC generates the plots directly** as
PNG and SVG files -- there is no need to run the R scripts separately.
